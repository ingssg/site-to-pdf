# 크롤링 속도 개선 방안

이 문서는 200페이지 크롤링이 느릴 때 고려할 수 있는 최적화 옵션을 정리한다.

## 1) 크롤링 동시성(가장 큰 체감 효과)

- **동시 페이지 처리**: 지금은 링크를 순차적으로 방문하므로 전체 시간이 길다.
- 개선 방향: 큐 + 작업자(worker) 방식으로 **N개 페이지를 동시에 크롤링**.
- 주의: Lambda 메모리/CPU와 Chromium 안정성에 맞춰 동시성 값을 조절해야 함.
  - 현재 기본값은 `concurrentPages = 2`

### 자동 분할 기준(배치 크롤링)

- UI 변경 없이 **내부 로직에서 자동 분할**하는 기준.
- 기준:
  - **N ≤ 60**: 1회 처리
  - **60 < N ≤ 120**: 2회 분할 (50% / 50%)
  - **120 < N ≤ 180**: 3회 분할 (40% / 40% / 20%)
  - **N > 180**: 60페이지 단위 배치 반복
- 배치 완료 시 다음 배치를 Lambda가 자동 재호출.

## 2) 이미지/스크린샷 처리 비용 줄이기

- **스크린샷 품질/해상도 낮추기**
  - `quality`, `viewport`, `fullPage` 옵션 조정
- **fullPageScreenshot 조건부 실행**
  - 법적 증거가 필요 없는 경우 fullPage 스킵
- **이미지 로딩 대기 최소화**
  - `document.fonts.ready`, 이미지 eager 로딩 등의 대기 시간을 축소

## 3) 네트워크/대기 시간 최적화

- `page.goto` **timeout 상향보다는 waitUntil 변경**
  - `domcontentloaded` 유지, `networkidle`는 피함
- 불필요한 `waitForTimeout` 제거/축소
  - 현재 여러 단계 대기(500ms/1000ms 등) 존재
- **리소스 차단**
  - 광고/트래커/폰트/비디오 등 필요 없는 리소스 요청 차단

## 4) 페이지 수집 범위 제한

- **Smart Mode 필터 강화**
  - 불필요 페이지를 더 적극적으로 스킵
- **maxDepth 조절**
  - 깊이가 깊어질수록 시간이 급증

## 5) 브라우저/컨텍스트 관리

- **컨텍스트 재사용 vs 페이지 재사용**
  - 안정성/속도 균형 필요
- **single-process 비활성화 유지**
  - 크래시 방지로 인한 재시도 비용을 줄임

## 6) 데이터 저장 최적화

- **스크린샷은 Storage에 저장** (DB payload 축소)
  - DB 업데이트 지연/타임아웃 방지로 전체 시간 단축

## 7) Lambda 리소스 확장

- **메모리/CPU 증설**
  - Lambda는 메모리 증설 시 CPU도 함께 증가
  - Playwright/Chromium 작업 속도 개선

---

## 우선순위 추천

1. 동시성 도입 (큐 + worker)
2. 스크린샷 비용 축소 (quality/viewport/fullPage 조건)
3. 리소스 차단 (광고/폰트/비디오)
4. Lambda 메모리 상향
