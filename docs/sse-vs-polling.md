# SSE vs 폴링: 가능성/비용/적합성

이 문서는 현재 구조(Next.js + Vercel + Lambda 비동기 작업)에서 SSE 적용 가능성과 비용 효율을 정리한다.

## 결론 요약

- **SSE 적용은 가능하지만 운영 난이도와 제약이 있다.**
- **비용 효율은 트래픽 패턴에 따라 달라진다.**
- 현재 구조에서는 **폴링을 유지하되 응답 경량화/폴링 간격 최적화**가 가장 현실적이다.

## 1) SSE 적용 가능성

### 가능

- SSE는 HTTP 단방향 스트림이라 **클라이언트 → 서버** 한 방향만 유지하면 된다.
- 진행 상황처럼 **서버에서 이벤트를 푸시**하는 용도에 적합.

### 제약

- **Serverless 환경에서 장시간 연결 유지**가 어려움.
- Vercel/Next 환경은 **함수 실행 시간이 제한적**이며, 연결 유지는 인프라 제약을 받음.
- **CloudFront/프록시/타임아웃**에 따라 연결이 끊길 수 있음.
- Lambda 작업은 **별도 프로세스**에서 돌기 때문에, SSE 서버가 **실시간으로 상태를 중계**할 구조가 필요.

즉, 단순히 API 라우트만 SSE로 바꾸는 것만으로는 부족하고,
**상태 저장소(Supabase 등) + SSE 브로커 역할**을 추가로 설계해야 한다.

## 2) 비용 효율성 비교

### 폴링

- 장점: 구현/운영이 단순.
- 단점: 진행률이 자주 바뀌지 않는데도 **요청이 계속 발생**.
- 비용: **요청 수에 비례**해 증가 (API 호출 + DB 조회).

### SSE

- 장점: 상태 변경 시에만 전송 → **불필요한 요청 감소**.
- 단점: **연결 유지 비용** 발생 (장시간 열린 연결).
- 비용: **동시 접속 수가 많을수록** 유지 비용이 커짐.

따라서:

- **짧은 작업/낮은 동시성**이면 폴링이 유리.
- **긴 작업/높은 빈도의 상태 변경**이면 SSE가 유리할 수 있음.

## 3) 현재 구조에 대한 판단

- 현재는 **Lambda에서 장시간 작업**을 하고,
- **프론트는 상태를 조회**하는 구조다.
- Vercel에서 SSE를 사용하면 **연결 유지 제약/타임아웃**이 리스크.

따라서 비용/안정성 측면에서 **폴링 최적화가 우선**이다.

### 권장 폴링 최적화

- 진행 중일 때만 폴링 (완료 후 중단)
- 백오프 적용: `2s → 4s → 8s` 등
- **응답 경량화** 유지 (이미 적용됨)

## 4) 폴링 백오프 상세 (프로젝트 적용 방안)

### 백오프란?

- **처음엔 짧은 간격**, 시간이 지날수록 **간격을 점진적으로 늘리는** 방식.
- 장시간 작업에서 **불필요한 요청을 줄여 비용을 절감**한다.

### 우리 프로젝트 적용 방식 (권장)

- 크롤링/요약 **시작 직후**: 2초 간격
- **진행률 변화가 느릴 때**: 4초 → 6초 → 8초로 증가
- **상태 변화 감지 시**: 간격을 다시 2초로 리셋
- **완료/에러**: 즉시 폴링 중단

### 적용하면 좋은 점

- **요청 수 감소** → Supabase/서버 비용 절감
- **타임아웃 리스크 완화** → 짧은 간격 유지 필요 감소
- 사용자 입장에서는 **초반 반응성 유지**, 후반에는 **비용 효율** 개선

### 구현 메모 (프론트 기준)

- 상태가 `crawling | summarizing | generating_pdf`일 때만 폴링
- `progress.percentage`가 **증가하면 간격 리셋**
- 일정 시간 변화가 없으면 **간격 증가**

## 4) SSE를 쓰려면 필요한 것

1. **SSE 전용 서버/라우트** (장시간 연결 유지 가능한 환경)
2. **상태 브로커** (Supabase 변경 감지 or Redis Pub/Sub)
3. **프론트 재연결/재시도 로직**
4. **장시간 연결 타임아웃 대응**

## 결론

현 시점에서는 **폴링 최적화가 가장 비용 효율적이며 안정적**이다.  
SSE는 **운영 복잡도와 인프라 제약을 해결할 수 있을 때** 고려하는 것이 좋다.
