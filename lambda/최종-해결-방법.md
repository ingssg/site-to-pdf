# Runtime.InvalidEntrypoint 최종 해결 방법

## 현재 상황
- CMD 재정의를 모두 비워뒀는데도 여전히 `Runtime.InvalidEntrypoint` 에러 발생
- Dockerfile의 CMD 설정과 관계없이 에러 발생

## 해결 방법

### 방법 1: Dockerfile에서 CMD 제거 (시도 중)

AWS Lambda Node.js 베이스 이미지는 자동으로 `index.handler`를 찾습니다.
Dockerfile에서 CMD를 제거했습니다.

**다음 단계:**
1. Docker 이미지 재빌드 및 푸시
2. Lambda 함수에 새 이미지 배포
3. Lambda 콘솔에서 CMD 재정의를 `index.handler`로 명시적으로 설정

### 방법 2: Lambda 콘솔에서 CMD 재정의 명시적 설정

CMD 재정의를 비워도 에러가 발생한다면, 명시적으로 설정해보세요:

1. Lambda 콘솔 → `site-to-pdf-worker2` 함수 선택
2. **"이미지"** 탭 클릭
3. **"이미지 구성"** → **"편집"** 클릭
4. **"CMD 재정의"** 필드에 `index.handler` 입력 (문자열 형식)
5. **"저장"** 클릭

### 방법 3: 이미지 재배포 확인

이미지를 수정했다면 반드시 재배포해야 합니다:

1. Lambda 콘솔 → **"이미지"** 탭
2. **"새 이미지 배포"** 버튼 클릭
3. 최신 이미지 태그 선택 (`latest`)
4. **"저장"** 클릭
5. 배포 완료까지 몇 분 대기

## 단계별 실행

### 1단계: Docker 이미지 재빌드 및 푸시
```bash
cd lambda
./build-and-push.sh
```

### 2단계: Lambda 함수에 새 이미지 배포
1. Lambda 콘솔 → **"이미지"** 탭
2. **"새 이미지 배포"** 클릭
3. `latest` 태그 선택
4. **"저장"** 클릭

### 3단계: CMD 재정의 설정
1. **"이미지 구성"** → **"편집"** 클릭
2. **"CMD 재정의"**에 `index.handler` 입력
3. **"저장"** 클릭

### 4단계: 테스트
1. **"테스트"** 탭에서 **동기식**으로 테스트
2. CloudWatch Logs 확인

## 예상 결과

### 성공 시
- `Runtime.InvalidEntrypoint` 에러가 사라짐
- `[Lambda] 워커 시작` 로그가 출력됨
- 함수가 정상적으로 실행됨

### 여전히 실패하는 경우
다음을 확인하세요:
1. **이미지 URI**가 최신 이미지를 가리키는지
2. **아키텍처**가 올바른지 (`x86_64`)
3. CloudWatch Logs의 **전체 에러 메시지**
4. `index.js` 파일이 이미지에 포함되어 있는지

## 추가 확인 사항

### 이미지에 파일이 포함되어 있는지 확인
Dockerfile에서 다음 파일들이 복사되는지 확인:
- `index.js` ✅
- `crawler.js` ✅
- `ai.js` ✅
- `pdf.js` ✅

### index.js 핸들러 확인
```javascript
exports.handler = async (event) => {
  // ...
};
```

이 형식이 올바른지 확인하세요.

## 참고

### AWS Lambda Node.js 베이스 이미지
- `public.ecr.aws/lambda/nodejs:20`는 자동으로 `index.handler`를 찾습니다
- 하지만 Container Image를 사용할 때는 Lambda 콘솔에서 CMD 재정의를 명시적으로 설정하는 것이 더 안전할 수 있습니다

### CMD 재정의 형식
- Lambda 콘솔: `index.handler` (문자열)
- Dockerfile: `CMD ["index.handler"]` (배열 형식, 현재는 제거됨)
