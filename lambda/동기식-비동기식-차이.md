# 동기식 vs 비동기식 호출 차이

## 현재 상황
- **비동기식**: 성공 ✅
- **동기식**: 실패 ❌ (`Runtime.InvalidEntrypoint`)

## 차이점

### 동기식 (Synchronous) 호출
- Lambda 함수가 **완료될 때까지 기다림**
- 함수의 **반환값을 즉시 받음**
- 함수 실행 중 에러가 발생하면 **즉시 에러 반환**
- 타임아웃: 최대 15분

### 비동기식 (Asynchronous) 호출
- Lambda가 함수를 **큐에 넣고 즉시 RequestId 반환**
- 함수의 **실제 실행 결과와 관계없이 호출은 "성공"**
- 함수는 **백그라운드에서 실행**
- 실제 에러는 CloudWatch Logs에서 확인 가능

## 중요: 비동기식 "성공"의 의미

⚠️ **비동기식으로 "성공"했다고 해서 함수가 정상 실행된 것은 아닙니다!**

비동기식 호출 시:
1. Lambda가 함수를 큐에 넣음 → **"성공"** 표시
2. 함수가 실제로 실행될 때 여전히 `Runtime.InvalidEntrypoint` 에러 발생 가능
3. 실제 실행 결과는 **CloudWatch Logs에서 확인**해야 함

## 확인 방법

### CloudWatch Logs 확인
1. Lambda 콘솔 → **"모니터링"** 탭
2. **"CloudWatch에서 로그 보기"** 클릭
3. 최신 로그 스트림 확인
4. 비동기식 호출 후에도 `Runtime.InvalidEntrypoint` 에러가 있는지 확인

### 실제 함수 실행 여부 확인
비동기식으로 호출한 후 CloudWatch Logs에서:
- ✅ `[Lambda] 워커 시작` 로그가 있으면 → 함수가 정상 실행됨
- ❌ `Runtime.InvalidEntrypoint` 에러가 있으면 → 함수가 여전히 실패함

## 왜 동기식은 실패하고 비동기식은 "성공"하는가?

### 동기식 호출
```
사용자 → Lambda 호출 → 함수 실행 시도 → Runtime.InvalidEntrypoint 에러 → 즉시 에러 반환
```

### 비동기식 호출
```
사용자 → Lambda 호출 → 함수를 큐에 넣음 → 즉시 RequestId 반환 ("성공")
                                    ↓
                            백그라운드에서 실행 시도
                                    ↓
                            Runtime.InvalidEntrypoint 에러 (사용자에게는 보이지 않음)
```

## 해결 방법

### 1. CloudWatch Logs 확인
비동기식으로 호출한 후에도 실제로 함수가 실행되었는지 확인:
- 로그에 `[Lambda] 워커 시작`이 있는지 확인
- `Runtime.InvalidEntrypoint` 에러가 여전히 있는지 확인

### 2. CMD 재정의 확인
이전에 설정한 CMD 재정의가 올바른지 확인:
- Lambda 콘솔 → **"이미지"** 탭
- **"이미지 구성"** → **"CMD 재정의"** 확인
- 비워두기 (`-`) 또는 `index.handler` 설정

### 3. 이미지 재배포
CMD 재정의를 수정했다면:
- 이미지가 자동으로 재배포되었는지 확인
- 필요시 **"Deploy new image"** 클릭

## 결론

**비동기식으로 "성공"했다고 해서 문제가 해결된 것은 아닙니다.**

다음을 확인하세요:
1. ✅ CloudWatch Logs에서 실제 함수 실행 여부 확인
2. ✅ `Runtime.InvalidEntrypoint` 에러가 여전히 있는지 확인
3. ✅ CMD 재정의 설정 확인

만약 CloudWatch Logs에서도 에러가 없다면, 그때 진짜 성공입니다! 🎉
