# 페이지 관리 전략 분석

## 페이지를 닫는 이유 (일반적인 경우)

### 1. 메모리 관리

- 각 페이지는 DOM, 이미지, 스크립트 등을 메모리에 유지
- 페이지를 닫으면 메모리 해제
- **하지만**: Lambda 환경에서는 함수가 끝나면 자동으로 정리됨

### 2. 리소스 정리

- 네트워크 연결, 타이머, 이벤트 리스너 등 정리
- **하지만**: 브라우저를 닫으면 모든 것이 정리됨

### 3. 브라우저 안정성

- 너무 많은 페이지가 열려있으면 브라우저가 느려질 수 있음
- **하지만**: 최대 5페이지 정도면 문제 없음

## Lambda 환경의 특성

### 장점

- **함수 종료 시 자동 정리**: Lambda 함수가 끝나면 모든 리소스가 자동으로 정리됨
- **충분한 메모리**: 2048MB 할당되어 있음
- **제한된 실행 시간**: 최대 15분이므로 장기 실행 문제 없음

### 단점

- **`@sparticuz/chromium`의 `single-process` 모드**: 페이지를 닫을 때 브라우저가 닫힐 수 있음

## 현재 문제

`@sparticuz/chromium`의 `single-process` 모드에서:

- `page.close()` 호출 시 브라우저 전체가 닫힐 수 있음
- 이는 버그이거나 `single-process` 모드의 제한사항

## 해결 방안 비교

### 방안 1: 페이지를 닫지 않음 (현재 적용)

**장점:**

- 브라우저가 안정적으로 유지됨
- 구현이 간단함

**단점:**

- 메모리 사용량 증가 (하지만 Lambda에서는 문제 없음)
- 페이지가 계속 열려있음 (하지만 함수 종료 시 정리됨)

### 방안 2: 페이지를 재사용

**장점:**

- 메모리 효율적
- 브라우저 안정성 유지

**단점:**

- 구현이 복잡함
- 페이지 간 상태 공유 문제

### 방안 3: 페이지를 닫되 브라우저 보호

**장점:**

- 메모리 효율적
- 리소스 정리

**단점:**

- `single-process` 모드에서 작동하지 않을 수 있음
- 브라우저가 닫힐 위험

## 결론 및 권장 사항

**Lambda 환경에서는 방안 1 (페이지를 닫지 않음)이 가장 안전합니다.**

이유:

1. **함수 종료 시 자동 정리**: Lambda 함수가 끝나면 모든 리소스가 자동으로 정리되므로 메모리 누수 걱정 없음
2. **충분한 메모리**: 2048MB 할당되어 있어 5-10개 페이지 정도는 문제 없음
3. **안정성 우선**: 브라우저가 닫히는 것보다 메모리를 조금 더 사용하는 것이 나음
4. **구현 단순성**: 복잡한 로직 없이 안정적으로 작동

**최종 정리:**

- 크롤링 중: 페이지를 닫지 않고 계속 사용
- 크롤링 완료 후: `close()` 메서드에서 모든 페이지 일괄 정리

이 방식이 Lambda 환경에 가장 적합합니다.
